# mindRID V19.0 — Account-deletion correction

## What changed
- `app.js` invokes the `delete-account` Supabase Edge Function with an explicit deletion confirmation, then clears local session/UI state only after a successful response.
- `supabase/functions/delete-account/index.ts` is a thin Supabase Edge Runtime adapter; `core.mjs` contains the dependency-injected workflow that is simulated by the bundled Node test.
- The server validates the bearer token and independently enforces AAL2 when the account has a verified TOTP factor. A frontend-only MFA check is not treated as a security boundary. CORS is restricted to mindRID production origins and localhost development origins.
- The function temporarily deactivates the profile to close the media-upload race. The accompanying migration blocks Storage insert/update for deactivated profiles. If a failure occurs, the function attempts to restore the profile's previous state.
- The function enumerates only the authenticated user's UUID folder, handles nested folders and pagination, rejects unsafe entry names, removes media through the Supabase Storage API in batches, then performs a second sweep for uploads already in flight.
- `MIGRATION-V19.0-ACCOUNT-DELETION.sql` hardens Storage insert/update policies and revokes client execution of the legacy deletion RPC.

## Deployment sequence

This sequence briefly disables the old account-deletion button while the replacement is being switched over. Do not let users initiate deletion during deployment.

1. Back up the deployed website files and database state. Do not run the full `schema.sql` against the live database for this patch.
2. From the Supabase project linked to `https://clqjbxpojrkwduyegwsc.supabase.co`, deploy the function directory: `supabase functions deploy delete-account --project-ref clqjbxpojrkwduyegwsc`. Ensure `index.ts` and `core.mjs` are both present in the function directory.
3. Confirm the Edge Function environment has `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY`. Manage these in Supabase; never embed the service-role key in browser code.
4. Apply `MIGRATION-V19.0-ACCOUNT-DELETION.sql` in Supabase SQL Editor. It updates the two Storage write policies and revokes client execution of the legacy RPC. The new site has not been deployed yet, so the old button will fail during this short switch-over window.
5. Deploy the website files from this package, preserving the existing Supabase URL/key in `app.js`. `index.html` now has a V19.0 cache-busting version.
6. Run the read-only permission verification query in the migration comments. Expected: `anon_can_execute=false`, `authenticated_can_execute=false`; `service_role_can_execute` should remain true if it was explicitly granted before.
7. Review Supabase Edge Function logs after a controlled staging-account deletion before treating the workflow as production-verified.

## Safety boundaries and limitations
- Do not disable or bypass `storage.protect_objects_delete`.
- Do not call `DELETE FROM storage.objects` directly.
- Do not test by deleting a real user's account.
- The workflow is not a single database transaction. If media removal succeeds but deleting the Auth user fails, the function attempts to restore the previous profile state; retry is designed to be safe.
- The function has a per-request enumeration ceiling of 100,000 storage entries and a maximum folder nesting depth of 32. If exceeded, it fails closed and does not delete the Auth user.
- This package has not been deployed to the live project. Node simulations do not replace an Edge Runtime compile/deploy check or a controlled staging verification.

See `AUDIT-V19.0-ACCOUNT-DELETION.md` for the findings, controls, test evidence, and residual risks.

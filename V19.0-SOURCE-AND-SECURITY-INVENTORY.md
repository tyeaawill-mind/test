# mindRID V19.0 — Source and Security/Data-Flow Inventory

**Baseline inspected:** `mindRID-V18.5-MOBILE-HOME-RESTORE.zip` (folder `mindRID-V18-FUTURE-CENTRIC/`)
**Scope:** source-level review of `schema.sql`, `MIGRATION-V17.sql`, `MIGRATION-V18.1.sql`, `MIGRATION-V18.2.sql`, `app.js`, `index.html`, and the packaged regression tests.
**Not in scope / not verified:** live Supabase project, applied migrations, live RLS flags/policies, Auth provider configuration, storage bucket state, production browser behavior, secrets/configuration outside this ZIP, backups, logs, edge functions not included in this package.

## Executive finding

The supplied source contains a substantial security foundation: owner-scoped private identity, visibility helper functions for Whispers, RLS policies for many tables, a private media bucket policy, and membership-scoped messaging policies. This is evidence of intended controls only; it does **not** prove those controls are installed or correct in the live project.

**Do not implement Mind Compass data collection or sensitive emotional inference yet.** First reconcile live schema/policies with this source, close the high-priority gaps below, and establish consent, retention, deletion, and export contracts.

## 1. Confirmed from supplied source

- `public.private_identity` is a separate table; its SELECT/INSERT/UPDATE/DELETE policies restrict rows to `user_id = auth.uid()` (schema.sql lines 42–47, 320–345).
- Whispers have `private`, `selected`, and `public` visibility; access is mediated by `mindrid_can_view_whisper(...)` (lines 49–59, 188–223, 351–374). The helper also checks blocks and deactivated profiles.
- Selected-recipient rows are readable by the recipient or Whisper owner, and recipient writes/deletes are owner-scoped (lines 379–416).
- Reports are insertable for visible targets and the reporter can read their own reports (lines 447–472). The same source also allows a reporter to delete their own report; see risk below.
- Blocks are scoped to the blocker for SELECT/INSERT/DELETE; helper logic treats a block as mutual for Whisper visibility and conversation creation (lines 169–186, 474–492, 143–146).
- Messaging uses a `mindrid_start_conversation` RPC and membership helper, with RLS policies on conversations, conversation members, and messages (lines 104–130, 132–167, 711–731).
- Media rows are scoped by Whisper/comment visibility and ownership. The schema declares a non-public `mindrid-media` bucket and storage policies for read/write/update/delete (lines 595–706).
- `whisper_media` declares `is_preview` and `preview_mode` in `schema.sql` (lines 595–607); `MIGRATION-V18.2.sql` adds these columns if missing and adds the `preview_mode` check constraint.
- The app contains account deactivation and password reset flows; schema source contains account lifecycle RPCs, including deactivation/reactivation/deletion (app.js around `doDeactivate`, schema.sql around lines 1003–1017).
- Composer UI contains an `@` suggestion interaction, but a UI mention is not the same as a consent-backed mention system.

## 2. High-priority source findings

### H1 — `circle_messages` lacks an explicit RLS-enable statement in the supplied schema

- `circle_messages` is created around schema.sql lines 849–855.
- A `circle_messages_select_member` and `circle_messages_insert_member` policy are defined around lines 928–929.
- The source's `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` list does not include `public.circle_messages` (the nearby list enables connections, groups, group_members, whisper_tags, and notifications; circle_messages is omitted).
- PostgreSQL policies do not enforce access when RLS is disabled. **Live impact is unknown until checked.** Verify `relrowsecurity` and effective policies in the live database immediately. If RLS is disabled, enable it and verify authenticated member-only read/write paths with two unrelated test accounts. Do not run a broad schema reapply as a substitute for this targeted check.

### H2 — Google sign-in is not implemented in the inspected client source

No `signInWithOAuth` / Google provider flow was found in `app.js`. This is a source finding, not a statement about Supabase dashboard configuration. V19 must implement the client flow and separately verify the provider, redirect URLs, email/account linking behavior, and callback handling in the live Supabase project.

### H3 — Mention/tag consent is not present as a defined workflow

The composer offers mention suggestions, but the inspected schema/app do not establish an explicit mention-consent record, recipient approval flow, or consent state machine. Before building consent behavior, decide what a mention means (plain text vs. notification/tag), whether it exposes identity, and whether recipients can approve, decline, remove, or disable mentions.

### H4 — Account export is not found in the inspected UI source

The app includes account deactivation/deletion-related functionality, but no user-facing account-data export flow was found in `app.js`. Verify the actual deletion RPC implementation and dependencies before changing it. Design export/deletion coverage for profiles, Whispers, replies, media/storage objects, messages, Circles, notifications, saves, history, connections/follows, and reports, including legal/abuse-retention exceptions where applicable.

### H5 — Reporter can delete their own report

The schema defines `reports_delete_own` for the reporter (around lines 470–472). That can remove a report from the queue if the live database has this policy and no separate immutable audit record exists. Decide whether user withdrawal should instead mark a report withdrawn while preserving moderation audit integrity. Verify operational moderation tooling before altering the policy.

### H6 — Group membership policy is broad

`group_members_select_related` allows any authenticated user to select group-membership rows (around line 922), rather than limiting reads to group members/owners. Assess whether this exposes participation patterns that users reasonably expect to be private. Define public/private Circle membership semantics and test them before Mind Compass shared constellations reuse group infrastructure.

## 3. Other risks / questions to resolve

- **Live drift:** migrations are separate from the base schema and may not all have been applied. Need a live schema/policy export and migration history before any schema changes.
- **Private media URL behavior:** the source stores `public_url` although the bucket is private; confirm this field is not a permanent public URL and that signed URLs are generated only after authorization, expire appropriately, and are not leaked into logs or notifications.
- **Block consistency:** check that blocks affect profile discovery, comments, direct messages, Circle invitations, notifications, and any future Compass recommendations consistently—not only the helper functions shown.
- **Sensitive fields:** profile schema includes location, background, interests, and a free-form `last_whisper_vibe`; define whether these are public, private, optional, or retained. Avoid reusing them as inferred emotional labels without explicit opt-in.
- **Function grants:** audit every `SECURITY DEFINER` function for execute grants, safe `search_path`, explicit authorization, and whether it can be invoked by `anon`/`authenticated`. The inventory is not a full adversarial SQL-function audit.
- **Deletion cascade:** verify storage objects are actually removed when media rows/users are deleted; SQL FK cascade does not itself guarantee object deletion in Supabase Storage.
- **Auth settings:** password reset is in the client; confirm redirect allowlists, confirmation behavior, MFA/AAL2 requirements, session lifetime, email enumeration protections, and provider settings in dashboard.
- **Data minimisation:** no Compass attention trails, emotional-root inference, habit profiling, or spiritual coaching records should be added before data purpose, consent, retention, correction/deletion, export, and access controls are agreed.

## 5. Prioritised V19 execution plan

1. **V19.0a — Live-state evidence collection (blocking):** obtain Supabase table/column inventory, `relrowsecurity`, policies, grants, function definitions/grants, bucket configuration, Auth providers/redirects, and migration history. Redact project secrets; never send service-role keys.
2. **V19.0b — Access-control test matrix:** test anonymous, owner, selected recipient, unrelated authenticated user, blocked user, Circle member, non-member, deactivated account, and deleted account against reads/writes for each sensitive object.
3. **V19.0c — Fix confirmed discrepancies only:** especially `circle_messages` RLS if absent, media URL behavior, report integrity, and overly broad membership visibility. Make narrow, reversible migrations with rollback notes.
4. **V19.1 — Mention consent + block/report/notification behavior:** define user-visible consent and notification settings; preserve existing product semantics where they work.
5. **V19.2 — Google sign-in and account lifecycle:** implement client OAuth, test live provider config, and verify deletion/deactivation/export requirements.
6. **V19 gate:** no Mind Compass collection of attention history, defensive-pattern interpretations, habit analytics, or faith-oriented coaching data until the privacy/data contract is approved and cross-account access tests pass.
